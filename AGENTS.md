# Памятка ИИ-агенту

Краткий контекст проекта, чтобы не перечитывать весь репозиторий в каждой сессии.
При расхождении этой памятки с кодом или задачей пользователя доверяй коду и
актуальной задаче. Не считай заметки о производительности гарантией FPS.

## Проект

Bonderium — Windows-приложение для интерактивной классической молекулярной
динамики. Интерфейс и сцена реализованы на Win32 и legacy OpenGL/WGL; код на
C++20. Пользовательские функции и ограничения модели описаны в `README.md` —
сверяйся с ним перед изменением поведения или документации.

## Карта кода

- `src/main.cpp` — окно, панели, ввод, камера, OpenGL-рендеринг, таймеры и UI-метрики.
- `src/simulation.h`, `src/simulation.cpp` — независимое от UI физическое ядро.
- `src/elements.h`, `src/elements.cpp` — таблица 118 элементов и свойства атомов.
- `src/updater.*` — проверка и загрузка обновлений.
- `tests/simulation_tests.cpp`, `tests/elements_tests.cpp` — тесты движка и элементов.
- `tests/performance_benchmark.cpp` — необязательный benchmark физики на 1k/5k/10k частиц.
- `CMakeLists.txt` — сборка приложения, тестов и benchmark.

## Важные ограничения и инварианты

- `simulation_engine` глобален и доступен UI, окну графиков и обработчикам
  сообщений. Не запускай `Engine::step()` в worker-потоке без отдельного
  дизайна синхронизации, снимков состояния и очереди команд.
- Симуляция и Win32 UI работают в одном потоке. Сохраняй ограниченный бюджет
  работы таймера; не добавляй неограниченный catch-up цикл.
- Движок использует список соседей Верле для короткодействующих сил и
  Barnes–Hut для достаточно крупных заряженных систем. Проверяй корректность
  физики существующими тестами при изменении этих участков.
- Рендерер использует legacy fixed-function OpenGL и display lists. Не
  предполагай наличие shader/instancing API; сохраняй совместимость и
  проверяй корректный жизненный цикл GL-ресурсов в активном контексте.
- Не смешивай дополнительный GDI `GetDC` с циклом `BeginPaint`/`SwapBuffers`;
  панели рисуются в текущем paint-контексте.
- Размеры интерфейса и DPI требуют осторожности: обработчик DPI пересоздаёт
  шрифты, но не весь layout автоматически. Не утверждай, что адаптивный layout
  завершён без проверки всех панелей.
- Температура, энергия и параметры элементов используют приведённые/
  эвристические единицы, а не точную квантовую химию. Не представляй модель
  как научно откалиброванную.

## Сборка и проверки

Типичная локальная сборка (Windows, CMake):

```powershell
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build --parallel
ctest --test-dir build --output-on-failure
```

Для benchmark добавь при конфигурации `-DBONDERIUM_BUILD_BENCHMARKS=ON`,
собери цель `PerformanceBenchmarks` и запусти `.\build\PerformanceBenchmarks.exe`.
Измерения зависят от CPU и фоновой нагрузки; физический benchmark не измеряет
полный FPS OpenGL-сцены и не подтверждает результат на другом ПК. Не
переустанавливай зависимости, если конфигурация и сборка проходят.

## Рабочий процесс

1. Начни с `git status --short`, чтобы сохранить чужие изменения; не отменяй и
   не перезаписывай незнакомый diff.
2. Читай только нужные участки кода и соответствующую часть `README.md`;
   избегай полного повторного сканирования проекта без причины.
3. Делай небольшие связанные изменения, сохраняй существующие стили и ошибки
   показывай явно.
4. Запускай минимальные проверки, покрывающие правку; для физики — также
   `SimulationTests`, для таблицы элементов — `ElementTests`.
5. Не заявляй о FPS/совместимости со «слабыми ПК» без измерения на целевом
   оборудовании. Не создавай коммит или релиз, если пользователь этого не просил.
